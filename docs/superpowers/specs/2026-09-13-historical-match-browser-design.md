# 历史比赛浏览设计

## 1. 文档状态

- 日期：2026-09-13
- 状态：设计已确认，等待实施计划
- 模块：历史比赛查询 API 与前端历史比赛页面
- 数据库：DuckDB

## 2. 背景与目标

历史数据导入模块已经能够把 Football-Data 的真实比赛、比分和市场赔率写入 DuckDB，但前端目前仍是基础骨架，用户无法在页面中检查已导入的数据。

本模块建立一个完整的只读浏览闭环：后端按条件分页查询历史比赛，前端通过“历史比赛”导航展示真实数据。第一版面向数据核验，不进行预测、回测或自动购票。

## 3. 范围

### 3.1 第一版包含

- 历史比赛独立页面和可用的侧边栏入口；
- 当前数据库的数据量摘要；
- 按联赛、赛季和球队名称筛选；
- 按开赛时间倒序排列；
- 服务端分页，每页默认 20 场；
- 表格直接展示开赛时间、联赛、赛季、主客队、半场比分、全场比分和收盘胜平负赔率；
- 展开行展示大小球、亚洲让球、赔率来源、阶段、可用时间和时间精度；
- 加载、空数据、请求失败和无筛选结果状态；
- 桌面端表格与窄屏横向滚动；
- 后端和前端自动测试。

### 3.2 第一版不包含

- 比赛详情独立路由；
- 排序字段自由切换；
- 高级赔率走势图；
- CSV 导出；
- 历史回测、模型概率或投注建议；
- 在浏览页面触发批量导入。

## 4. 方案选择

采用服务端分页方案。前端只请求当前筛选条件下的一页数据，后端在 DuckDB 中完成筛选、计数和排序。

不采用一次性返回全部比赛的方式，因为数据扩展到多个联赛和赛季后，响应体和浏览器渲染成本会持续增加。第一版也不引入通用数据表格框架，避免为当前固定列需求增加不必要的依赖。

## 5. 后端设计

### 5.1 查询接口

新增：

```text
GET /api/data/matches
```

查询参数：

| 参数 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `page` | 正整数 | `1` | 当前页码 |
| `page_size` | 正整数 | `20` | 每页数量，最大 100 |
| `competition` | 字符串 | 空 | 来源联赛代码，例如 `E0` |
| `season` | 字符串 | 空 | 赛季代码，例如 `2324` |
| `team` | 字符串 | 空 | 主队或客队名称的包含匹配 |

响应包含：

- `items`：当前页比赛；
- `page`、`page_size`：实际分页参数；
- `total_items`：符合条件的比赛总数；
- `total_pages`：总页数；
- `filters`：当前数据库中可选的联赛和赛季，用于构建前端筛选器。

每场比赛包含：

- 稳定比赛 ID；
- 联赛代码和名称；
- 赛季、开赛时间；
- 主客队名称；
- 半场与全场比分；
- 市场数组，每项包含市场类型、盘口、来源、提供方、阶段、采集时间、可用时间、时间精度和赔率选项。

市场数据只读取 `stage = closing` 的快照。无法验证为开球前可用的 Football-Data 收盘赔率仍保留 `kickoff_bound` 标记，前端必须如实展示，不能称为赛前赔率。

### 5.2 查询与组合

仓储层分两步读取当前页：

1. 查询符合条件的比赛总数和当前页比赛；
2. 使用当前页的比赛 ID 批量查询市场快照和选项，再在应用层按比赛组合。

这样避免比赛、快照和赔率选项直接多表连接造成一场比赛重复成多行，也避免逐场查询产生 N+1 查询问题。

球队筛选使用参数化 SQL，对主队和客队名称进行不区分大小写的包含匹配。所有筛选值均作为数据库参数传入，不拼接进 SQL。动态 SQL 只负责添加预先定义的筛选片段。

### 5.3 输入与错误处理

- 页码小于 1、每页数量超出 1 至 100 时，由 FastAPI 参数校验返回 422；
- 未知联赛或赛季按“没有匹配数据”处理，返回空列表而不是服务器错误；
- 团队搜索去除首尾空格，空白字符串等同于未筛选；
- 数据库读取失败时记录服务端日志，对外只返回安全的 `internal_error`；
- 空数据库返回 `items = []`、`total_items = 0` 和空筛选项。

## 6. 前端设计

### 6.1 信息结构

侧边栏新增“历史比赛”入口并标记为可用。“历史回测”继续保留为待建功能，明确区分事实数据浏览和模型回测。

历史比赛页面从上到下包含：

1. 页面标题和真实数据说明；
2. 数据摘要卡片：比赛数、球队数、市场快照数、最新比赛时间；
3. 筛选栏：联赛、赛季、球队关键词和清除筛选；
4. 历史比赛表格；
5. 分页控件和结果范围说明。

### 6.2 表格

主表格列为：

| 列 | 内容 |
|---|---|
| 日期 | 本地化开赛日期与时间 |
| 联赛 / 赛季 | 联赛名称、来源代码和赛季 |
| 主队 | 来源中的真实球队名称 |
| 半场 | 半场主客队比分，无数据时显示短横线 |
| 全场 | 全场主客队比分 |
| 客队 | 来源中的真实球队名称 |
| 收盘 1 / X / 2 | 主胜、平局、客胜赔率，无数据时显示短横线 |
| 操作 | 展开或收起市场详情 |

展开区按市场类型展示：

- 胜平负；
- 2.5 球大小球；
- 亚洲让球及盘口；
- 来源、提供方、阶段；
- `captured_at`、`available_at` 和 `time_precision`。

`kickoff_bound` 在中文界面解释为“仅能确认开球时可用”，用警示样式提示它不能用于开球前回测。

### 6.3 状态与交互

- 初次加载显示表格骨架，不显示虚构数据；
- 请求失败显示简短错误和“重新加载”按钮；
- 数据库为空时说明需要先执行历史数据导入；
- 筛选后无结果时保留筛选栏，并提供清除筛选按钮；
- 修改筛选条件时回到第一页；
- 上一页和下一页在边界处禁用；
- 同一时间只展开用户选择的比赛，降低页面信息密度；
- 使用 `AbortController` 取消已过期请求，避免快速筛选时旧响应覆盖新结果。

页面沿用现有绿色研究工作台视觉语言，不伪造队徽，不使用装饰性图片。窄屏保持表格语义并提供横向滚动，不把复杂赔率表强行压缩成难以阅读的卡片。

## 7. 前后端数据流

```text
用户打开“历史比赛”
  -> 前端并行请求数据摘要和比赛第一页
  -> 后端校验分页与筛选参数
  -> DuckDB 查询总数、当前页比赛和相关市场
  -> 后端组合为稳定响应结构
  -> 前端渲染摘要、筛选项和表格

用户修改筛选
  -> 前端取消旧请求并重置到第一页
  -> 请求新的服务端分页结果
  -> 更新表格与分页状态
```

## 8. 代码边界

后端：

- 在导入仓储中增加只读比赛查询方法；
- 在数据路由中增加请求参数和响应模型；
- 查询组装逻辑保持在仓储层，HTTP 状态映射保持在路由层。

前端：

- 将 API 地址和请求逻辑保持独立；
- 将历史比赛页面、筛选栏和表格拆成职责清晰的组件；
- `App` 只负责顶层导航和页面选择，不承载数据库字段转换逻辑。

第一版不引入 React Router。当前只有两个可访问页面，使用 URL hash 保存页面选择即可；如果后续增加比赛详情、模型和回测路由，再统一引入正式路由库。

## 9. 测试策略

遵循测试驱动开发，先写失败测试，再实现功能。

后端测试覆盖：

- 默认分页和开赛时间倒序；
- 页码、每页数量和总页数；
- 联赛、赛季和球队筛选；
- 半场与全场比分；
- 当前页市场批量组合；
- 无赔率、无数据和未知筛选；
- 非法分页参数返回 422；
- 数据库异常不泄露内部信息。

前端测试覆盖：

- “历史比赛”导航可访问；
- 加载后展示真实比赛字段和摘要；
- 筛选会产生正确请求并重置页码；
- 展开区展示盘口和时间精度说明；
- 加载、空数据、无筛选结果和错误状态；
- 分页按钮的边界状态与请求行为。

最终运行完整后端测试、前端 Vitest、ESLint、TypeScript 生产构建和 `git diff --check`。

## 10. 验收标准

1. 用户可以从侧边栏打开“历史比赛”页面。
2. 页面展示 DuckDB 中的真实比赛，不含示例或虚构数据。
3. 默认按开赛时间倒序，每页展示 20 场。
4. 用户可以按联赛、赛季和球队筛选，并清除筛选。
5. 表格展示半场、全场和收盘胜平负赔率。
6. 展开区展示大小球、亚洲让球和完整时间语义。
7. `kickoff_bound` 数据明确提示不能用于开球前回测。
8. 数据量增长时仍由服务端分页，不一次返回全部比赛。
9. 空数据、无结果、加载和失败状态均有明确反馈。
10. 自动测试和静态检查全部通过。
11. 不实现预测模型、回测逻辑或自动购票。

## 11. 后续顺序

历史比赛浏览完成后，项目按以下顺序推进：

1. 优化 DuckDB 批量写入性能；
2. 导入更多真实联赛和完整赛季；
3. 增加数据质量页面与异常检查；
4. 定义无未来信息泄漏的训练数据集和回测切分；
5. 经过数据验收后，再设计和实现首个基线预测模型。
