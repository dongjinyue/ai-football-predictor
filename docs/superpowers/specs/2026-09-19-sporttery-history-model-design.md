# 中国竞彩历史奖金采集与首版预测模型设计

## 1. 文档状态

- 日期：2026-09-19
- 状态：对话设计已确认，等待书面规格确认
- 数据范围：2015 年至今的中国竞彩官方足球数据
- 首次验收范围：2015-01-01 至 2015-12-31
- 首版预测目标：胜平负与总进球概率
- 数据库：DuckDB

## 2. 目标与成功标准

建立一条可重复执行、可中断恢复、来源可追溯的中国竞彩历史数据管道，保存比赛、赛果和固定奖金的完整历史变化，并据此生成严格按预测时点截断的训练样本。

第一版模型输出：

- 胜平负的主胜、平局、客胜概率；
- 总进球的 `0`、`1`、`2`、`3`、`4`、`5`、`6`、`7+` 概率；
- 开球前 24、12、6、1 小时四个预测时点的独立结果。

成功不以单纯命中率判断。模型必须使用时间外测试集，并与同一时点的市场隐含概率基线比较 Log Loss、Brier Score 和概率校准。模型不能稳定超过基线时，应如实报告，不发布“优于市场”的结论。

## 3. 数据来源与使用边界

### 3.1 官方接口

已验证的主要接口为：

- `getUniformMatchResultV1.qry`：按日期分页读取比赛、联赛、球队、竞彩编号和赛果；
- `getFixedBonusV1.qry`：按官方 `matchId` 读取各玩法固定奖金历史。

详情页使用的官方接口可作为开球时间的补充来源，但只有能够证明字段含义与时区时才写入 `kickoff_at`。页面当前展示的阵容、排名、近期状态或伤停，如果没有历史发布时间，不进入首版训练集。

### 3.2 已确认的访问行为

腾讯云 EdgeOne 会对 Python 默认的 `Python-urllib` 客户端标识返回 HTTP 567。相同请求使用正常、固定且可识别的客户端标识后返回 HTTP 200；不需要登录 Cookie。采集器设置明确的 `User-Agent`、`Accept` 和对应官方页面 `Referer`，但不绕过验证码、登录、付费墙或交互式安全验证。

### 3.3 玩法范围

全部保存来源实际返回的玩法：

- `hadList`：胜平负；
- `hhadList`：让球胜平负；
- `ttgList`：总进球；
- `crsList`：比分；
- `hafuList`：半全场；
- `singleList`：单关等状态信息，作为元数据保存，不伪装成赔率快照。

首版只训练胜平负和总进球。其他玩法先完整保存，后续可作为辅助特征或新预测目标。

## 4. 采集架构

新增 `backend/app/sporttery/`，保持各模块单一职责：

- `client.py`：设置请求头、超时、有限重试和错误分类；
- `catalog.py`：把日期范围拆成稳定窗口并生成分页请求；
- `models.py`：定义不可变的比赛、官方元数据和奖金快照记录；
- `parser.py`：将来源 JSON 转换为统一记录并校验字段；
- `repository.py`：执行幂等写入、检查点和覆盖率查询；
- `service.py`：协调列表、详情、奖金历史、原始文件和数据库事务；
- `jobs.py`：后台运行、进度读取和安全停止。

### 4.1 请求顺序

```text
日期窗口
  -> 分页读取比赛列表
  -> 保存列表原始 JSON
  -> 提取并去重 matchId
  -> 补充官方比赛详情与准确开球时间
  -> 读取每场固定奖金历史
  -> 保存原始 JSON
  -> 解析并事务写入统一数据库
  -> 更新检查点和覆盖率报告
```

列表默认使用 7 天窗口和来源允许的分页大小。代码必须服从接口实际返回的 `pages`，不能假设固定页数。

### 4.2 请求节奏与恢复

- 单线程请求，不并发批量冲击来源；
- 每个网络请求之间默认等待 3 至 5 秒；
- 对连接超时、HTTP 429 和 5xx 使用有上限的指数退避；
- HTTP 567 视为来源安全策略阻断，记录检查点并停止当前任务，不持续重试；
- 已存在且校验通过的原始响应不再次下载；
- 每完成一个列表页或一场详情即写入检查点；
- 重启后从最后一个未完成项目继续，不重复写入数据库。

2015 全年可能产生数千次详情请求，任务预计需要数小时。进度以已发现比赛、已完成详情、失败、缺失和剩余数量展示，不以固定完成时间承诺。

## 5. 原始数据与审计

原始响应按来源事实不可变保存：

```text
data/raw/sporttery/
  match_lists/2015/{begin}_{end}/page-{page}.json
  match_details/2015/{match_id}.json
  fixed_bonus/2015/{match_id}.json
  checkpoints/2015.json
```

每个文件同时记录：

- 请求 URL 的规范化标识，不包含秘密信息；
- HTTP 状态和来源业务错误码；
- 下载时间；
- SHA-256 校验值；
-解析状态和安全错误代码；
- 重试次数。

原始 JSON、检查点和数据库不提交到 Git。

## 6. 统一数据库映射

### 6.1 复用现有核心表

- `competitions`：`source = sporttery`，官方联赛 ID 作为来源联赛标识；
- `teams` 与 `team_aliases`：保留体彩中文队名和规范化别名；
- `matches`：`source = sporttery`，`source_match_id = matchId`；
- `market_snapshots`：一行表示一次官方奖金更新时间下的一个玩法；
- `market_outcomes`：保存该玩法的全部结果与奖金值。

来源更新时间按 `Asia/Shanghai` 解析，再转换为 UTC 存储：

- `captured_at`：`updateDate + updateTime`；
- `available_at`：与官方更新时间相同；
- `time_precision = exact`；
- `stage = pre_match`，但任何晚于或等于开球时间的记录均不用于赛前训练，并在质量报告中单独列出。

### 6.2 官方元数据

新增竞彩比赛元数据表，保存：

- 统一比赛 ID；
- 官方 `matchId`、竞彩编号和比赛日期；
- 官方联赛 ID；
- 让球线；
-销售、取消、赛果和派奖状态；
- 开球时间的来源字段与证据精度。

新增通用请求审计表记录每个列表页、详情和奖金接口的采集状态。数据库唯一约束保证同一个 `matchId`、玩法、更新时间和结果不会重复。

### 6.3 市场与选项代码

| 来源字段 | 市场代码 | 选项代码示例 |
|---|---|---|
| `hadList` | `match_result` | `home`、`draw`、`away` |
| `hhadList` | `handicap_result` | `home`、`draw`、`away`，让球存于快照层 |
| `ttgList` | `total_goals` | `0` 至 `6`、`7_plus` |
| `crsList` | `correct_score` | `1_0`、`0_0`、`other_home` 等 |
| `hafuList` | `half_full` | `home_home`、`draw_away` 等九项 |

方向标记字段仅用于验证相邻记录的升降关系，真实奖金值和官方更新时间才是训练事实。

## 7. 数据校验与实体边界

解析阶段校验：

- `matchId`、球队、联赛和比赛日期存在；
- 主客队不同；
- 完赛比分为非负整数；
- 奖金为有限正数；
- 同一快照中的必要结果完整；
- 更新时间可以解析且按时间非递减；
- 让球线与让球玩法绑定；
- 取消或延期比赛不生成训练标签。

体彩与 Football-Data 的球队不能仅凭模糊名称自动合并。首版使用体彩内部稳定身份训练；未来引入跨来源特征时，通过日期、联赛、主客队和人工审核过的别名表匹配。

## 8. 训练样本与防泄漏

### 8.1 样本时点

对每场有准确开球时间的比赛生成 T-24h、T-12h、T-6h、T-1h 四个候选样本。每个样本只读取 `available_at <= cutoff_at` 的记录，并选择该时点之前最近一次完整快照。

若当时尚未开售或没有历史记录，该玩法记为缺失。禁止使用预测时点之后的记录回填。样本保存所选快照 ID、快照年龄和截止时间，便于审计。

### 8.2 特征

市场特征包括：

- 当前奖金与去除返还率影响后的隐含概率；
- 初始奖金到当前奖金的绝对和相对变化；
- 上一个预测时点以来的变化；
- 调整次数、升降次数和最近调整距预测时点的时间；
- 让球胜平负及总进球市场在相同截止时间下的状态；
- 缺失标记与报价陈旧时间。

球队历史特征只从该场比赛之前的体彩完赛比赛计算：

- 最近 5 场和 10 场胜平负、进球和失球；
- 主客场拆分表现；
- 休息天数；
- 联赛与赛季类别。

本场最终比分、赛后统计、未来比赛、预测时点之后的奖金以及无历史时间证据的页面状态严禁作为输入。

### 8.3 标签

- 胜平负：由官方全场比分生成 `home`、`draw`、`away`；
- 总进球：由全场主客队进球之和生成 `0` 至 `6`、`7_plus`。

标签生成代码必须与输入特征查询隔离，防止赛果字段进入特征集合。

## 9. 模型与评估

第一版训练两个独立多分类模型。先实现可解释基线，再实现树模型：

1. 市场基线：胜平负使用对应隐含概率；总进球使用总进球奖金转换后的概率；
2. 简单统计基线：基于球队历史的多分类模型；
3. 市场与走势模型：使用奖金、变化和球队历史特征的梯度提升树，并进行概率校准。

评估指标：

- Log Loss 为主要指标；
- Brier Score 和校准曲线检查概率质量；
- 准确率、混淆矩阵作为辅助；
- 与同一预测时点市场基线的差值；
- 按联赛、预测时点和数据缺失程度分组报告。

训练、验证和测试必须按比赛时间顺序切分。2015 全年首次采集只验证管道并训练实验模型；完成多年采集后再使用较早年份训练、后续年份验证、最新完整年份测试。

模型文件保存到 `models/`，同时记录训练数据时间范围、特征版本、代码版本、指标和随机种子。不得只保存一个无法复现来源的二进制模型。

## 10. 2015 全年首次验收

首次真实运行范围固定为 `2015-01-01` 至 `2015-12-31`。运行完成后输出：

- 列表窗口、页面和来源报告的比赛总数；
- 唯一 `matchId` 数及重复数；
- 详情与奖金接口成功、缺失、失败和跳过数量；
- 五种玩法的比赛覆盖率和快照数量；
- 每场快照数的最小值、中位数和高分位数；
- 有准确开球时间的比例；
- 可生成 T-24h、T-12h、T-6h、T-1h 样本的比例；
- 无效奖金、时间倒序、赛后更新和取消比赛数量；
- 原始文件数、校验结果与数据库幂等性结果。

验收抽查至少包括：

- 比赛列表与数据库的 `matchId`、球队和赛果一致；
- 奖金历史原始 JSON 与数据库全部快照一致；
- 重跑同一范围不会增加重复比赛或快照；
- 中途停止后能从检查点继续；
- 默认 Python 客户端被 HTTP 567 拦截的回归测试，以及配置请求头后的成功模拟测试。

如果来源对全年度采集触发安全限制，保留已取得的数据和检查点，报告实际完成范围，不以提高并发、伪造 Cookie 或绕过交互验证继续采集。

## 11. 自动测试与集成验证

常规自动测试不依赖体彩在线接口，使用脱敏的小型 JSON 固定样例覆盖：

- 分页、空页和业务错误解析；
- 五种玩法映射；
- 奖金和时间校验；
- 时区转换；
- 幂等导入和事务回滚；
- 断点恢复；
- HTTP 567、429、超时和结构变化；
- 四个预测时点的严格截断；
- 赛果标签与特征隔离；
- 时间顺序数据切分。

在线集成检查只请求少量已知比赛，单独运行，不作为日常测试的必要条件。

## 12. 非目标

第一阶段不包含：

- 自动投注、投注建议或收益承诺；
- 绕过验证码、登录、付费或网站安全挑战；
- 使用无历史时间证据的伤停、阵容或排名；
- 自动猜测跨数据源球队身份；
- 用 2015 单年实验结果宣称模型已经具备稳定实战能力。
