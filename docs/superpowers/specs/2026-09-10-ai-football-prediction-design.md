# AI 竞彩足球预测系统设计说明

## 1. 文档状态

- 状态：已确认设计，等待用户评审正式文档
- 日期：2026-09-10
- 项目暂定名称：AI Football Predictor
- 第一阶段运行方式：本地部署
- 前端：React + TypeScript
- 后端与模型：Python + FastAPI

## 2. 项目目标

构建一个面向中国体育彩票竞彩足球受注赛事的 AI 预测与分析系统。系统每日获取受注赛事和带时间戳的 SP 数据，结合历史比赛、球队实力、近期状态、联赛差异和市场信息，生成以下玩法的概率：

- 胜平负；
- 让球胜平负；
- 比分；
- 总进球数；
- 半全场。

系统是分析与研究工具，不自动购票、不控制投注账户、不承诺盈利。预测页面必须展示数据更新时间、数据质量、模型置信度和风险提示。

## 3. 核心设计原则

### 3.1 统一概率来源

系统不为每种玩法训练互不相关的分类器。机器学习模型首先预测上下半场的主客队进球参数，概率模型随后生成半场与全场联合比分分布，各玩法从同一分布推导，避免结果互相矛盾。

### 3.2 双模型并行

系统同时维护两类模型：

1. 纯足球模型：只使用球队、联赛、赛程、阵容和历史表现；
2. 市场辅助模型：在纯足球特征基础上加入体彩 SP 及其他合法获得的赛前赔率。

页面分别显示两个模型的结果和差异，防止将市场信息误称为模型独立发现的规律。

### 3.3 全赛事接入、分质量预测

系统尝试接入体彩出现的全部竞彩足球赛事，但不假设所有赛事的数据同样完整。预测前根据数据完整性分级，并选择相应的降级策略。

### 3.4 时间一致性

任一预测只能使用预测时刻之前已知的数据。比赛特征、积分、近期状态、阵容和 SP 均需记录可用时间，训练与回测禁止未来信息泄漏。

## 4. 范围与边界

### 4.1 第一阶段包含

- 体彩受注赛事导入与定时更新；
- 多来源历史比赛数据导入；
- 联赛、球队和赛事统一标识；
- 带时间戳的 SP 快照；
- Elo、泊松和市场隐含概率基线；
- CatBoost、LightGBM 或 XGBoost 进球模型；
- Dixon–Coles、双变量泊松或负二项比分分布；
- 胜平负、让球胜平负、比分、总进球和半全场概率；
- 严格的时间回测、概率校准和模型比较；
- React 本地网页；
- 每日预测、单场详情和历史回测页面。

### 4.2 第一阶段不包含

- 自动购票或投注账户操作；
- 承诺收益或所谓稳赚策略；
- 实时滚球预测；
- 视频识别和球员轨迹分析；
- 大语言模型微调；
- 未经许可复制、再发布或商业化受限制的数据。

## 6. 模块划分

### 6.1 数据采集模块

职责：

- 获取体彩当日受注赛事；
- 定时保存 SP 和让球变化；
- 导入历史比分、半场比分和赛事属性；
- 更新完场赛果；
- 保存数据来源、采集时间和许可信息；
- 对网络失败、页面结构变化和重复数据进行记录与重试。

采集器与业务逻辑隔离。每个数据源实现统一接口，以便某个来源失效时替换，而不修改模型代码。

### 6.2 实体匹配模块

职责：

- 将体彩联赛名称映射为标准联赛 ID；
- 将不同来源的球队中文名、英文名和别名映射为标准球队 ID；
- 通过比赛时间、主客队和赛事识别同一场比赛；
- 保存人工修正记录，避免以后重复处理；
- 对低置信度匹配进入人工审核队列。

实体匹配是全赛事覆盖的关键基础。无法可靠匹配的比赛不得输出高置信度预测。

### 6.3 数据存储模块

本地第一阶段使用 DuckDB 保存分析数据，并将原始文件保留在独立目录。核心实体包括：

- `competitions`：赛事和联赛；
- `seasons`：赛季；
- `teams`：标准球队；
- `team_aliases`：球队别名；
- `matches`：比赛与赛果；
- `market_snapshots`：带时间戳的 SP/赔率；
- `lineups`：阵容及其公布时间；
- `features`：按预测时间生成的特征快照；
- `predictions`：预测结果；
- `model_versions`：模型、训练区间和参数；
- `data_quality_reports`：缺失和匹配质量。

未来云端部署时可迁移到 PostgreSQL，业务接口保持不变。

### 6.4 特征工程模块

主要特征：

- 球队动态 Elo、进攻强度和防守强度；
- 最近 5、10、20 场状态；
- 经对手实力修正的进球、失球、xG 和 xGA；
- 主客场表现和中立场；
- 休息天数、赛程密度和旅行影响；
- 联赛平均进球、平局率和主场优势；
- 杯赛阶段、双回合状态和赛季阶段；
- 阵容实力、伤停和教练变化（数据允许时）；
- 初始 SP、最新 SP、变化幅度和去除返还率后的隐含概率。

所有滚动特征必须先错开当前比赛再计算，保证本场结果不会进入本场输入。

### 6.5 模型模块

#### 基准模型

- 最常见类别；
- 联赛历史平均概率；
- Elo；
- 独立泊松；
- 市场隐含概率。

#### 机器学习模型

第一候选为 CatBoost，原因是它适合表格数据及类别特征，并能处理部分缺失值。LightGBM 和 XGBoost 作为对照模型。模型预测：

- 主队上半场进球参数；
- 客队上半场进球参数；
- 主队下半场条件进球参数；
- 客队下半场条件进球参数。

#### 比分分布模型

优先比较 Dixon–Coles、双变量泊松与负二项模型。验证集以对数损失和校准结果选择，不预先认定最复杂模型一定最好。

#### 模型集成

集成权重只在时间验证集上确定。最终测试集仅用于一次性评估，不参与模型或权重选择。

### 6.6 体彩玩法转换模块

- 胜平负：汇总全场比分矩阵中主胜、平局和客胜区域；
- 让球胜平负：按照当时公布的整数让球修正主队得分后汇总；
- 比分：映射体彩比分选项，并合并其他胜、其他平和其他负；
- 总进球：汇总 0、1、2、3、4、5、6 和 7+；
- 半全场：由半场和全场联合分布汇总九种组合。

所有玩法按90分钟及伤停补时计算，不包含加时赛和点球大战。

### 6.7 评估与回测模块

数据按时间划分，不随机打散：

- 训练集：较早赛季；
- 验证集：后续赛季，用于参数和集成选择；
- 测试集：最新完整时间段，用于最终报告；
- 日常监控：采用向前滚动回测。

指标包括：

- 胜平负：Accuracy、Macro F1、Log Loss、Brier Score 和校准；
- 比分：Top-1、Top-3、Top-5、真实比分概率和 Log Loss；
- 总进球：Accuracy、MAE、Log Loss 和分组召回率；
- 半全场：Accuracy、Macro F1、Log Loss 和混淆矩阵；
- 市场研究：模型与市场概率差异、模拟收益、最大回撤和样本量。

指标需按联赛、数据等级、月份和模型版本分组展示。模拟收益不能替代概率质量指标。

### 6.8 Web 前端

采用 React + TypeScript，构建工具优先选择 Vite。页面包括：

1. 今日赛事：筛选联赛、开赛时间、数据等级和预测倾向；
2. 单场详情：双方实力、近期表现、概率矩阵、市场差异和主要驱动因素；
3. 历史回测：按玩法、联赛和模型版本展示指标；
4. 数据质量：展示无法匹配、字段缺失和数据过期问题；
5. 模型管理：展示当前模型版本、训练区间和更新时间。

前端只显示后端返回的预测与解释数据，不在浏览器中重新计算模型概率。

## 7. 数据质量与降级策略

| 等级 | 可用数据 | 预测策略 |
|---|---|---|
| A | 历史、近期表现、阵容和市场完整 | 完整集成模型 |
| B | 历史比赛完整，缺少阵容或 xG | 机器学习进球模型 |
| C | 历史较少，仅有比分和赔率 | Elo、泊松和市场模型 |
| D | 球队无法可靠匹配或数据过期 | 不给强结论，显示数据不足 |

置信度不能只取最高预测概率。它还需综合数据等级、模型分歧、校准误差和训练分布外程度。

## 8. 每日数据流

1. 获取体彩当日受注赛事；
2. 规范化联赛与球队名称；
3. 检查和人工处理低置信度匹配；
4. 保存初始 SP 快照；
5. 更新历史比赛、球队评分和可用阵容；
6. 在指定预测时间生成不可变特征快照；
7. 运行纯足球模型和市场辅助模型；
8. 生成五类玩法概率并校准；
9. 保存预测、输入摘要和模型版本；
10. 前端展示预测与风险提示；
11. 完场后更新赛果并进入回测数据库。

## 9. 错误处理与可追溯性

- 网络或来源失败：保留上次成功时间并标记数据过期，不静默使用旧数据；
- 球队匹配失败：进入人工审核，不自动创建疑似重复球队；
- 特征缺失：按模型声明的降级路径处理并记录原因；
- 模型加载失败：回退到经过验证的上一版本；
- 概率异常：要求所有概率非负、总和归一，并通过一致性测试；
- 每次预测保存数据截止时间、模型版本、特征版本和代码版本。

## 10. 安全、合规与责任边界

- 尊重数据来源的许可、访问频率和再发布限制；
- 不在代码仓库提交密钥、令牌或受限制的原始数据；
- 网页明确标注预测的不确定性和数据时间；
- 不提供自动购票能力；
- 不使用“稳赚”“必中”等描述；
- 若未来提供公开服务，需要重新审查数据授权、隐私和当地法律要求。

## 13. 实施阶段

### 阶段一：数据骨架与可信基准

- 初始化工程、配置和测试框架；
- 设计统一数据表；
- 导入历史比赛；
- 实现球队与联赛映射；
- 实现 Elo、泊松和市场基准；
- 建立时间回测框架。

### 阶段二：机器学习进球模型

- 建立无泄漏特征流水线；
- 训练并比较 CatBoost、LightGBM 和 XGBoost；
- 生成半场与全场联合比分分布；
- 映射体彩全部玩法；
- 完成概率校准。

### 阶段三：体彩每日工作流

- 接入受注赛事；
- 保存 SP 时间快照；
- 自动匹配比赛；
- 定时更新预测；
- 建立失败重试和人工审核入口。

### 阶段四：React 前端

- 今日赛事；
- 单场详情；
- 概率与市场对比；
- 回测看板；
- 数据质量和模型版本页面。

### 阶段五：联赛扩展与运行监控

- 增加更多合规数据源；
- 扩充球队别名；
- 监控各联赛数据和模型漂移；
- 对数据不足的赛事自动降级；
- 为后续云端部署预留接口。

## 14. 验收标准

- 能导入体彩当天全部受注赛事；
- 能输出球队与联赛匹配结果及置信度；
- 每场比赛具有数据质量等级；
- 能生成五种玩法且概率相互一致；
- 纯足球和市场辅助预测独立展示；
- 回测严格遵守时间边界；
- 所有核心指标可重复计算；
- 每次预测可追溯到数据、模型和代码版本；
- React 页面能够查看今日赛事、单场详情和历史回测；
- 数据不足或数据过期时明确提示，不输出误导性的高置信结论。

## 15. 后续决策点

以下事项在对应实施阶段通过验证后决定，不阻塞当前架构：

- 历史数据源的最终组合与授权范围；
- 体彩页面采用公开接口、允许的页面读取还是人工导入作为稳定兜底；
- CatBoost、LightGBM 与 XGBoost 的最终选择；
- Dixon–Coles、双变量泊松与负二项分布的最终选择；
- 图表库采用 Plotly 还是 ECharts；
- 本地验证完成后的云端部署平台。
